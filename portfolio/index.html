Two programs that take the hardware at its word.

A CUDA sparse-matrix kernel that refuses to reformat your data before multiplying it, and a Vulkan simulator that carries the full Stokes vector across thirteen wavelengths before it ever decides what colour the sky is. Both are C++, both are measured rather than asserted.

Project — CUDA / C++20

VarBlockSpMM

Sparse × dense multiplication that executes directly on packed variable-size blocks — heights and widths independently anywhere in {8, 16, …, 64} — with no CSR expansion, no fixed-block retiling, no output atomics, and no temporary workspace.

CUDA 12.6+C++20CMake 3.25 cuSPARSE / cuBLAS baselinesRTX 5060 Ti

Libraries want your matrix in their layout. If your application already produces dense variable blocks — as boundary-element and covariance near-field assemblies do — the conversion is pure overhead, paid again whenever the matrix changes. VarBlockSpMM keeps the layout you already have and writes the kernel around it: wide panels share input tiles across rows and reuse each sparse value across RHS columns, while widths 8 and 16 drop to a 64-thread CTA with full-panel accumulation, a choice made by measured comparison rather than intuition.

1.139× geometric-mean speedup over the fastest tested library across the full 128-case core on three matrix seeds, winning 308 of 384 individual-product comparisons. Startup from prepared host formats — including one completed product — is 3.953× faster than the best library alternative, and compact scalar CSR needs 1.948× the device storage.

The evidence is the point. 168 synthetic configurations in three fresh processes each; a 768-process follow-up campaign; published Harwell-Boeing matrices; twelve generated covariance near-field matrices with geometry-derived partitions; a full factorial mapping/accumulator/CTA ablation at RHS 8. Benchmark runners verify a build receipt tying compiled source hashes to the actual executable bytes, and the analyzers reject checksum, design, command, process and timing inconsistencies before a single table is emitted. Where the libraries win — BSR8 in steady state on the native component — the README says so first.

Project — Vulkan / C++26

Vulkanic

A real-time polarized-sky simulator: thirteen-band spectral Stokes-vector successive-order scattering, Rayleigh plus Lorenz–Mie, with a runtime camera analyzer that switches between linear and elliptical polarization.

Vulkan 1.2 computeC++26Win32, no framework GLSL → SPIR-Vno RT hardware

Most renderers treat polarization as a post-process and the sky as a gradient; the models that do it properly live offline in radiative-transfer packages. Vulkanic puts one in a window you can look around. Radiance is transported as Stokes vectors (I, Q, U, V) through up to four scattering orders with proper Mueller matrices and frame rotations, and only after the analyzer does it become CIE 1931 XYZ and then linear sRGB.

The numerics are hand-written: a Lorenz–Mie solver bakes the aerosol scattering matrix at startup, a droplet-size-weighted Debye/Fresnel table drives the bows, and even the JSON config parser is in-repo. The dependency list is vk-bootstrap and VMA. Everything else — window, input, math, spectral integration — is written out.

Edits to path_tracer_config.json are polled each frame and apply live; changing an aerosol parameter rebuilds the Mie table without a restart. A binary earth-shadow test puts twilight points behind the planet's limb into umbra, which is what gives the terminator its edge, and a configurable Lambertian ground reflects attenuated sunlight back into the polarized atmosphere.

Because "it looks faster" is not a measurement, there is a benchmark mode that disables input, GUI and hot reload, records Vulkan timestamps per pass after warm-up, and reports mean / median / p95. --capture-hdr dumps the raw linear accumulation buffer, and a standard-library-only comparison tool diffs two captures against explicit absolute and relative tolerances.

How I work

Claims come with their raw records attached.

Both projects are native C++ against a low-level API — CUDA and Vulkan — written without a framework in the middle, and both are built so a stranger can reproduce the numbers. VarBlockSpMM ships the campaign data, the analyzers that reject inconsistent records, and a paper build that regenerates every table from them. Vulkanic ships a deterministic benchmark mode and a bit-level HDR comparison tool.

The other half of that is saying where the approach loses. Direct block execution is slower than BSR8 in steady state on the native component, and the sky simulator has no scene geometry at all. Both README files lead with those limits rather than burying them.
